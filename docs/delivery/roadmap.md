# Delivery roadmap

Status: proposed · Updated: 2026-09-21 · Implementation: not implemented

This is the proposed V1 sequence. It describes requirements, not completed implementation. The web app keeps its existing React/Vite routes, settings, design system, and dossiers interface; the VPS-hosted APIs adapt its data access. The [web-only decision](../decisions/0007-web-only-platform.md) and [self-hosted platform decision](../decisions/0008-self-hosted-platform.md) supersede the earlier companion and Trigger Cloud proposals while preserving those records as history.

## V1 journey

1. [Login](steps/01-login.md)
2. [Onboarding](steps/02-onboarding.md)
3. [Set up a profile using AI](steps/03-ai-profile.md)
4. [First scout](steps/04-first-scout.md)
5. [Check matches](steps/05-check-matches.md)

V1 succeeds when an approved pilot user can sign in, connect their own AI, confirm a profile, run a public-source search, and inspect persisted matches in the existing dossiers UI. The user can open a posting from that interface. Copying an apply prompt and other application mechanisms are post-V1.

Resolve each step's open decisions before implementation. Domain documents own business rules; architecture documents own shared mechanisms. Dated research remains evidence and does not imply that a provider or source passed its proof gate.

## Delivery dependencies and proof gates

- **Pilot identity:** configure Google sign-in and passwordless email codes; any verified email may sign in. Verified email is the identity key; never link an account on an unverified email. Provision one private workspace per authenticated user and reject cross-workspace reads and writes. See [Workspace](../domain/workspace.md), [identity and controlled data](../architecture/identity-and-data.md), and [platform-auth research](../research/platform-auth.md).
- **Own AI before profile creation:** target all four providers and their selected connection methods: OpenAI device login or API key; Gemini OAuth or API key; Anthropic pasted setup token or API key; xAI device login or API key. These are required provider targets, not proof of hosted compatibility or authorization. For each route, prove the intended credential exchange, encrypted hosted storage, least-privilege access, and an actual model call. Verify credential expiry or revocation where applicable, quota/rate-limit failures, and credential-free logs. Resolve provider product authorization independently. Do not silently reduce the provider set or switch accounts/billing routes. Until the selected connection works, preserve work as waiting for reconnect or an explicit manual switch. See [provider research](../research/provider-connections.md) and the [provider proof blockers](linear-backlog.md).
- **Profile confirmation and imports:** accept text-based PDFs and a manual questionnaire; scanned or unreadable PDFs fall back to manual entry, with no OCR. Confirm candidate facts explicitly, preserve unknowns, and never infer authorization, language proficiency, or unsupported claims. Profile and dossier imports need conflict review, deduplication, provenance, and known source dates; never invent transitions from incomplete legacy history. Keep profile editing and editable export. See [Candidate](../domain/candidate.md), [persistence](../architecture/persistence.md), and [step 03](steps/03-ai-profile.md).
- **Source proof:** before claiming V1 coverage, validate the Greenhouse, Lever, and Ashby public HTTP adapters against permitted representative boards, including pagination, source IDs/aliases, dates, descriptions, duplicate handling, partial/error outcomes, and retention of completed observations. Separately select and prove one permitted public browser source end to end through the VPS Browser Use runtime. Public-only means login walls and challenges are reported as blocked; there is no takeover or authenticated-board access in V1. Measure the initial source and run/capacity bounds in experiments. Track unmeasured thresholds and proof gaps as bounded blocker tickets; do not invent numeric limits. See [Discovery](../domain/discovery.md), [browser workers](../architecture/browser-workers.md), [discovery research](../research/job-discovery.md), and the [source proof blockers](linear-backlog.md).
- **Durable scout and match:** scout persists posting observations before handing independent, idempotent requests to evaluation. Scout completion does not wait for match completion. Retries must preserve results and not repeat completed work. Match pins immutable profile and posting inputs; the Python deterministic scorer remains. TypeSafe is the platform-funded default, with the user's selected AI as the fallback. Verify this exact fallback and its provider labeling. If that AI is unavailable, work waits for reconnect or explicit manual switch. See [Discovery](../domain/discovery.md), [Evaluation](../domain/evaluation.md), and [persistence](../architecture/persistence.md).
- **Existing dossiers UI:** use the current table, cards, filters, detail view, export, and Open posting action. Sort current accepted fit descending, publication date descending, and stable ID before pagination. When publication date is absent, use first discovery and label it accurately. Keep 0–10 scout coverage separate from 0–100 fit and evidence confidence; missing scores are unknown. Keep pending, failed, incomplete, and outdated work visible after current matches. Confirmed profile changes trigger reassessment; page reads never start model work. See [step 05](steps/05-check-matches.md) and [Evaluation](../domain/evaluation.md).

The complete journey must retain confirmed profile facts, imported provenance, postings, and accepted assessments across interruption and retry. A partial or failed source scan cannot close postings. A match threshold cannot delete discovery evidence. Model replay uses stored results and never repeats external effects. The [selective event-sourcing decision](../decisions/0002-selective-event-sourcing.md) is accepted but not implemented.

Measure source coverage, useful results, false or ambiguous matches, intervention rate, queue age, and cost per useful result. Browser minutes or successful task exits alone do not establish user value.

## Later delivery

Post-V1 review topics include copy-apply-prompt handoff, integrated preparation and submission, ATS execution, submission reconciliation, Gmail replies, recurring automation, and outcome analytics. This list preserves relevant domain examples; it is not a commitment to implement every mechanism or a selection of future architecture. Give each item a separate product and technical scope review before planning implementation. Applications and Communications domain documents retain proposed invariants and examples, but they do not select a companion or future execution mechanism. Resolve consent, authorization, source eligibility, and external-effect proofs only for topics selected to proceed.

- **Preparation, if selected:** scope validation for package generation, visible progress, unresolved answers, stale package/profile rejection, imported provenance, and immutable profile/posting inputs. See [Applications](../domain/applications.md).
- **Submission, if selected:** choose a supported ATS, confirmation evidence, reconciliation UX, and live-change policy. Prove package-bound authority, durable attempts, and crashes on either side of Submit. An uncertain outcome must never cause blind resubmission. Then smoke-test a permitted real form without submitting. See [Applications](../domain/applications.md#open-design-questions) and [browser research](../research/browser-applications.md).
- **Gmail replies, if selected:** scope an independently eligible provider data path, production requirements, backfill, retention, and correction rules. Prove consent, token refresh, history recovery, idempotent observations, offline classification, and deletion. Technical success does not establish provider approval. See [Communications](../domain/communications.md#open-design-questions) and [Gmail research](../research/gmail-connectors.md#spike-acceptance-criteria).
- **Recurring operation and feedback, if selected:** define duplicate-message, out-of-order-result, revoked-access, and missed-schedule behavior before expanding automation. Resolve observation precedence, freshness, profile publication, reassessment, and per-workspace usage limits. See [Discovery](../domain/discovery.md), [Candidate](../domain/candidate.md), [Evaluation](../domain/evaluation.md), and [scheduler research](../research/schedulers.md).
- **Optional Job Kit-funded general AI:** track a separate post-V1 ticket to decide whether to offer Job Kit-funded AI for profile or browser-agent work. This is distinct from TypeSafe, the selected platform-funded default match classifier, and does not replace V1's own-AI prerequisite. Record the decision in the [delivery backlog](linear-backlog.md).

Module documents own domain acceptance scenarios. Research documents retain provider-specific experiments; this roadmap links to them rather than copying their checklists. The Event Delivery Engine remains undecided and is not a dependency of this sequence.
