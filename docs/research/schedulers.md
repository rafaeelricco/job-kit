Research date: 2026-09-19. Scope: the easiest reliable TypeScript workflow layer for an individual job-seeker platform. This is an architecture recommendation, not an implementation commitment.

## Recommendation

The team should use **Trigger.dev Cloud** for the first release if managed hosting is acceptable. It offers typed tasks, runtime input schemas, and per-user schedules. It also offers a dashboard, retries, and wait tokens. Together these cover the expected discovery (scout → match) → draft → approval flow with less initial workflow machinery than Temporal. The team should keep PostgreSQL as the business source of truth and keep provider operations idempotent in application code.

This recommendation is specifically for Cloud. Trigger self-hosting currently lacks Cloud checkpoints, autoscaling, and warm starts, and introduces several operational components. A local AI executor backed by the user's subscription is a separate execution target. A cloud task should send an authorized job to the personal companion and wait for the result. It should not assume that a hosted worker can inherit the user's local provider subscription or browser session. Provider authorization remains a separate product requirement.

| Option            | Best reason to choose it                                                                  | Main cost or limit                                                                                                   |
| ----------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Trigger.dev Cloud | Fastest TypeScript task development and operations for a small team                       | Vendor hosting; retries/replays still need application idempotency; self-host differs materially                     |
| Inngest           | Durable event-driven functions while retaining your own HTTP or persistent-worker compute | Step/host runtime limits; distributed per-step execution; 24-hour built-in deduplication window                      |
| pg-boss           | PostgreSQL-only infrastructure and ordinary Node workers                                  | Human waits and process coordination need more application state; queue processing is not a complete workflow engine |
| Temporal          | Complex, long-lived processes, signals, durable timers, and explicit recovery semantics   | Deterministic workflow model, worker deployment/versioning, and greater learning/operations cost                     |

## Trigger.dev details that change the design

- `schemaTask` validates task payloads at runtime. Direct `task.trigger()` validates before creating a run; generic triggering validates before execution. Its schema input/output terminology includes schema transformations; the team should not infer automatic business-result validation. The team should parse model and tool results with its own result schema. [Schema tasks](https://trigger.dev/docs/tasks/schemaTask)
- Dynamic schedules support IANA timezones, `externalId`, and `deduplicationKey`. The deduplication key is project-scoped, so the key should include environment and workspace. The current free-plan schedule creation imposes at least hourly cadence and at least a 60-minute spreading window. The team should not promise an exact local delivery time without verifying the selected plan. [Scheduled tasks](https://trigger.dev/docs/tasks/scheduled)
- Trigger idempotency keys normally expire after 30 days. Failed runs clear the key; successful and cancelled runs retain it until expiry. Inside tasks, default key scope includes the parent run; the team should choose a deliberate global key for an application operation. These are execution deduplication aids, not a permanent business-operation ledger. [Idempotency](https://trigger.dev/docs/idempotency)
- A `concurrencyKey` provides per-key queue concurrency. Child tasks do not inherit their parent's queue, and checkpointed waits release concurrency. A concurrency limit of one therefore cannot lock a workspace through a multi-day approval lifecycle. The team should use application state for lifecycle exclusivity. [Queue concurrency](https://trigger.dev/docs/queue-concurrency)
- Task retries can repeat code and effects. The team should decompose work into bounded subtasks and make each effect safe to repeat. Provider concurrency and provider requests/tokens per minute are different controls: the team should maintain a shared quota limiter for actual provider calls. [Errors and retries](https://trigger.dev/docs/errors-retrying)
- Wait tokens support human/external completion, but default timeouts are short: the documented token wait default is ten minutes and token idempotency TTL is one hour. The team should set explicit approval deadlines, validate callback data, and authenticate the approving actor in Job Kit before completing a token. A callback URL is not the application's authorization layer. [Wait tokens](https://trigger.dev/docs/wait-for-token)
- Dashboard replay creates a new run using the payload and latest code. It is not historical deterministic replay. A replay must still encounter the same business operation IDs and refuse or reconcile effects already committed. [Replaying runs](https://trigger.dev/docs/replaying)
- `maxDuration` limits active execution; checkpoint waits do not consume it. A timeout can bypass task cleanup hooks, so the team should use resource TTLs and reapers for browser sessions and temporary files. [Maximum duration](https://trigger.dev/docs/runs/max-duration)
- Cloud and self-host feature parity is not complete. The team should review the documented missing checkpoint support before treating self-host as a drop-in cost escape route. [Self-hosting](https://trigger.dev/docs/self-hosting/overview)

## When alternatives win

**Choose Inngest** when Job Kit should keep all business compute on its own service or persistent workers. It also fits when Job Kit needs event-triggered functions, scoped concurrency, and queued throttling. Current TypeScript v4 supports schema-backed events, but the team should pin the SDK because examples and older documentation may use different APIs. Events/functions have a 24-hour built-in deduplication window. Throttling queues work; rate limiting can discard excess starts. Neither limits every provider request made inside one step. A step can run for up to two hours subject to its host's stricter timeout. Cancellation is observed between steps, so the current step can finish. [Deployment](https://www.inngest.com/docs/platform/deployment), [triggers and schemas](https://www.inngest.com/docs/reference/typescript/functions/triggers), [idempotency](https://www.inngest.com/docs/guides/handling-idempotency), [throttling](https://www.inngest.com/docs/guides/throttling), [limits](https://www.inngest.com/docs/usage-limits/inngest), [cancellation](https://www.inngest.com/docs/reference/typescript/functions/cancel-on)

**Choose pg-boss** if self-hosting and minimal infrastructure outweigh ready-made workflow tooling. It can enqueue work through an adapter in the same PostgreSQL transaction as business events, removing the broker handoff gap for that enqueue. Current docs also include job flows, timezone schedules, and keyed schedules. They also include heartbeats, cancellation signals, and retry policies. These features narrow the gap with task platforms, but human approval and resumable multistep business state still belong in an explicit application state machine. Documented global group concurrency can briefly exceed its target during races, so the team should not treat it as an exact external-provider quota. [Transaction adapters](https://pgboss.io/api/adapters), [jobs and flows](https://pgboss.io/api/jobs), [schedules](https://pgboss.io/api/scheduling), [workers](https://pgboss.io/api/workers)

**Choose Temporal** when durable process coordination becomes the core complexity: multiple long-lived signals, compensation, and versioned execution. Sophisticated cancellation and recovery across many services also count as core complexity. Its workflow replay reconstructs execution without re-running completed activities. Activity effects can still duplicate if the effect succeeds and reporting completion fails; activities need idempotency. Workflow code is deterministic and side effects belong in activities. TypeScript types alone do not runtime-validate incoming data. Scheduling supports overlap/catch-up policies; timezone matching has explicit DST behavior. [Workflow basics](https://docs.temporal.io/develop/typescript/workflows/basics), [activity semantics](https://docs.temporal.io/activity-definition), [message passing](https://docs.temporal.io/develop/typescript/workflows/message-passing), [schedules](https://docs.temporal.io/develop/typescript/workflows/schedules), [timezone specification](https://nodejs.temporal.io/api/interfaces/client.ScheduleSpec)

## Contract between PostgreSQL and any scheduler

1. The system should commit the domain event, workflow request, and outbox row in one PostgreSQL transaction. A workflow request contains a stable request ID, workspace, and workflow version. It also contains a capability scope and input references.
2. The system should dispatch using that stable ID as the scheduler idempotency key. It should save the returned run ID. It should retry ambiguous delivery using the same ID.
3. Before an external effect, the system should claim a durable `operation_id` with an input hash. It should store attempts, provider references, and outcomes. Provider idempotency keys, leases/fencing, and reconciliation address separate failure modes. A local dedupe row alone cannot resolve an effect that succeeded before its acknowledgment was lost.
4. The system should submit validated results through application commands that enforce workspace and expected-version rules. It should keep orchestration state separate from domain truth.
5. The system should order only the streams that require ordering, with explicit causal prerequisites or expected versions. Scheduler concurrency is not a guarantee of causal FIFO across an entire workspace.
6. The system should persist approvals with actor, workspace, input version, and decision before notifying the scheduler. It should handle early, duplicate, stale, and expired decisions explicitly.
7. The system should rebuild read models using a projector-only path that cannot emit workflow requests or repeat provider effects.
8. The system should store credential references and artifact IDs in task inputs. It should retrieve tenant secrets just in time, redact logs, and avoid credential material in histories, payload dashboards, and model prompts.
9. The system should persist browser context references with expiry. It should reconnect or recreate and revalidate the page after a human wait. It should not assume that a live browser process survives checkpointing.

## Required failure experiments before launch

- The team should kill the dispatcher after scheduler acceptance but before recording the run, then verify one business operation despite duplicate delivery.
- The team should redeliver after the scheduler's deduplication TTL and replay a run from the dashboard, then verify the permanent operation ledger prevents duplicate effects.
- The team should kill a worker after provider success but before persisting acknowledgment, then verify reconciliation or an explicit uncertain state rather than blind resubmission.
- The team should approve before a wait is registered, approve twice, approve from another workspace, and approve a stale draft, then verify only the authorized current decision proceeds.
- The team should cancel while queued, waiting, running, and completing an external effect, then verify both user-visible state and resource cleanup.
- The team should exercise DST transitions, overlapping daily schedules, and provider 429s. It should also exercise credential revocation, browser expiry, and a deployment during a pending approval.
- The team should rebuild every projection from events and verify that no email, browser submission, AI execution, or new scheduler run occurs.
